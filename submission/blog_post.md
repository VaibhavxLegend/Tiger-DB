# Building an Agentic Fraud Investigation System with TigerGraph

*Submitted for the TigerGraph Agentic AI Hackathon 2026*

## Overview
Fraud investigations suffer from unmanageable latency. In a legacy setup, anomalous alerts generated by real-time models require analysts to manually query multiple systems, correlate device fingerprints, and manually piece together "rings" before writing a SAR (Suspicious Activity Report). We built the **TigerGraph HHGOA System** to automate the time-intensive reasoning of fraud analysts by combining TigerGraph’s graph infrastructure with a robust LangGraph agent state machine. 

## Architecture

### Why TigerGraph as the Reasoning Substrate
Large Language Models struggle with dense, structured topological data. Instead of forcing the LLM to understand millions of transaction edges, we offloaded deterministic pattern detection to **TigerGraph**. TigerGraph natively identifies connected components (like shared devices across disparate cards) and velocity anomalies. The Agent then focuses strictly on synthesis and compliance.

### The Investigation Workflow
We designed a 7-node LangGraph state machine:
1. **trigger**: Captures case alerts.
2. **investigate**: Executes TigerGraph MCP tool calls for deep topological insights (e.g., getting N-hop neighborhoods, calculating graph-native risk signals).
3. **assess_uncertainty**: Queries the LLM to judge pattern match, probability, and evidence strength.
4. **gather_more_evidence**: The state machine operates a conditional loop to request `analyst_info` or `customer_validation` up to 3 times if evidence is insufficient.
5. **recommend_action**: Proposes auto/L1/L2 actions checked deterministically against the policy engine.
6. **explain**: Drafts full regulatory narratives (SAR) citing concrete evidence.
7. **update_memory**: Vectorizes the case and maps `SIMILAR_TO` edges back into the graph.

### Graph Schema Design
Our graph pivots around identifying the *attack vectors*: `Transaction`, `Card`, `Customer`, `Device`, `Address`, `EmailDomain`, and `Case`. This enables real-time lookups to instantly isolate fraud rings based on shared device or IP clusters—even if the underlying identities used completely different billing codes.

### Hybrid Retrieval: GraphRAG + Case Memory
When reasoning over a case, the LLM isn't just given rules; it is given *history*. We map real historical fraud patterns to the graph. The agent uses a hybrid retriever that blends Vector embedding lookup with Graph traversal (`get_similar_past_cases`) to surface context specifically mirroring the current topology. 

## Implementation Highlights

### Phase 1 & 2: Graph Foundation and MCP Server
We processed ~590k transactions into structured edges. We exposed these natively via an MCP (Model Context Protocol) Server. This standardized the input/output schemas the Agent needed to retrieve localized Graph traversals (e.g., `find_shared_devices`, `velocity_check`).

### Phase 3 & 4: LangGraph Agent & Benchmark
We successfully implemented the State Graph and tested it across the 20 required Hackathon benchmark cases. Due to robust LLM outputs combined with deterministic validation fallback loops, every case processed seamlessly and correctly routed through policy rules.

### Phase 5: Fast API & Plain-JS Trigger Console 
To make it tangible, we implemented a purely asynchronous FastAPI backend serving a lightweight single page application. This UI loads JSON case logs and allows analysts to manually trigger new cases against the live LLM state machine.

## What We Learned
Graph + LLM Synergy is incredible. Where graphs excel (infinitely tracing relationships and calculating exact risk factors deterministically in milliseconds), LLMs excel in unstructured narrative synthesis and handling nuanced ambiguities (deciding *if* a sequence violates written compliance policies).
